How to Learn System Design

System design is the art of turning a rough idea — "build something like Twitter" — into components that talk to each other reliably at scale. This is a visual map of the core ideas, the tradeoffs you'll keep re-fighting, and a roadmap for learning it in order.

The Five Pillars

Every system design conversation, no matter the product, keeps coming back to these five concerns.

📈

Scalability

Handling growth — more users, more data, more traffic — by adding resources (scale up) or machines (scale out).

🛡️

Availability

Staying up and responsive even when parts fail. Measured in "nines" — 99.9% uptime is ~8.7 hours of downtime a year.

🔄

Consistency

Making sure every reader sees the same (correct) data, even when it's replicated across many machines.

⚡

Latency & Throughput

How fast a single request completes, and how many requests the system can process per second.

🧩

Maintainability

Can a new engineer understand, extend, and safely change this system a year from now?

Tradeoffs You Can't Avoid

System design is rarely about finding the "right" answer — it's about picking which tradeoff fits the product's needs.

CAP Theorem

Consistency
Availability
Partition Tol.

During a network partition, you can only pick C or A — not both. Most real systems pick availability and accept eventual consistency.

SQL vs. NoSQL

Strong schema
Horizontal scale

Relational databases give you joins and transactions; NoSQL stores trade that structure for easier sharding and flexible schemas.

Latency vs. Freshness

Cache TTL long
Cache TTL short

Longer caching means faster responses but staler data. Every cache needs an explicit invalidation strategy.

Vertical vs. Horizontal Scaling

Bigger machine
More machines

Vertical scaling is simple but hits a ceiling and creates a single point of failure. Horizontal scaling requires stateless services.

Must-Know Terms

A quick-reference glossary for the words that show up in almost every system design discussion.

Load Balancer
Distributes incoming requests across multiple servers so no single machine gets overwhelmed.
Cache
A fast, temporary data store (often in-memory) that avoids repeating expensive computations or database reads.
Sharding
Splitting a database into smaller pieces ("shards"), each holding a subset of the data, to scale writes horizontally.
Replication
Keeping copies of the same data on multiple machines for redundancy and to scale read traffic.
CDN
Content Delivery Network — servers spread around the world that cache static content close to users.
Message Queue
A buffer (like Kafka or SQS) that lets services communicate asynchronously without waiting on each other.
Consistent Hashing
A technique for spreading keys across servers so adding/removing a server only reshuffles a small fraction of data.
Rate Limiting
Capping how many requests a client can make in a time window to protect the system from abuse or overload.
Idempotency
An operation that produces the same result no matter how many times it's retried — crucial for safe retries.
Eventual Consistency
A guarantee that all replicas will converge to the same value — eventually, not necessarily right away.
Single Point of Failure
Any component whose failure takes down the whole system. Good designs eliminate these through redundancy.
Horizontal Scaling
Adding more machines to share the load, instead of making one machine bigger (vertical scaling).

Before You Design Anything

A quick checklist to run through at the start of any system design exercise — interview or real project.

  • Clarify the requirements: what must it do, and what can it skip?
  • Estimate scale: how many users, requests per second, and how much data?
  • Define the API: what are the core read/write operations?
  • Sketch the high-level architecture before diving into details.
  • Pick a database and justify it with the access patterns.
  • Call out the bottleneck and how you'd scale past it.
  • Name the single points of failure and how to remove them.
  • State the tradeoffs out loud — there's rarely one right answer.
Keep this as a reference — system design is learned by revisiting the same ideas across many different problems.
